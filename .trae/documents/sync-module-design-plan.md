# 同步模块开发计划

## 一、需求概述

为 MiniObsidian 笔记应用实现完整的云同步模块，支持：
- **手动同步**：用户主动触发同步操作
- **自动同步**：后台定时同步，支持可配置间隔、网络检测、断点续传
- **跨设备同步**：在新设备上拉取云端笔记
- **选择性同步**：按文件类型、大小、路径过滤
- **冲突处理**：单文件多次修改场景的智能冲突解决

---

## 二、方案对比评估：百度网盘 vs OneDrive

### 2.1 评估维度

| 维度 | 百度网盘 API | OneDrive (Microsoft Graph) API | 本地文件夹同步 |
|------|-------------|-------------------------------|---------------|
| **OAuth 接入** | 需百度开放平台开发者账号，审核周期长 | 需 Azure 账号，注册即用 | 无需 OAuth |
| **文件版本控制** | 不支持原生版本控制 | 支持版本历史（`/versions`） | 依赖云盘客户端 |
| **增量同步** | 无 delta query，需全量扫描 | 支持 delta query（`/delta`） | 全量扫描 + hash 对比 |
| **冲突检测** | 无 ETag 机制，需自行比对 | 支持 ETag + `If-Match` 头 | 仅文件修改时间 |
| **单文件多次修改** | 上传覆盖，无法追溯历史 | 可查看/恢复历史版本 | 依赖云盘客户端版本控制 |
| **断点续传** | 支持分片上传 | 支持分片上传（`uploadSession`） | 文件系统级别，天然支持 |
| **速率限制** | 较宽松 | 严格（100 req/10s per app） | 无限制 |
| **存储空间** | 免费 5GB，会员 5TB | 免费 5GB，Microsoft 365 1TB | 取决于云盘客户端 |
| **用户门槛** | 需百度账号 + 授权 | 需微软账号 + 授权 | 无额外门槛 |
| **开发复杂度** | 高（OAuth + API 适配） | 高（OAuth + Graph API 适配） | 低（已有实现） |

### 2.2 单文件多次修改场景分析

**场景描述**：用户在多个时间段持续编辑同一个笔记文件。

| 方案 | 同步行为 | 数据安全性 | 用户体验 |
|------|---------|-----------|---------|
| **百度网盘 API** | 每次修改后上传覆盖，无法查看历史 | 低（无版本追溯） | 差（误操作无法恢复） |
| **OneDrive API** | 每次修改后上传，保留版本历史 | 高（可恢复任意版本） | 好（有版本回退） |
| **本地文件夹同步** | 文件变更后由云盘客户端同步 | 中（取决于云盘客户端） | 中（需依赖第三方客户端） |

### 2.3 方案结论

**推荐方案：以增强型本地文件夹同步为主，OneDrive API 为可选高级功能**

理由：
1. **用户无开发者账号**：百度网盘和 OneDrive 的直接 API 接入都需要注册开发者账号和 OAuth 配置，门槛较高
2. **本地文件夹同步零门槛**：用户只需安装百度网盘/OneDrive 客户端，设置同步目录即可
3. **增强 `sync_state` 表**：利用已有的数据库表实现增量检测、冲突追踪、同步状态持久化
4. **OneDrive API 作为可选扩展**：未来用户注册开发者账号后，可启用直接 API 同步，获得版本历史等高级功能

## 四、用户场景解决方案

### 场景 1：创建 → 删除 → 重建同名笔记

**问题**：两个版本都被同步到云端。

**解决方案**：
1. `sync_state` 表记录每个文件的同步状态和哈希值
2. 同步时检测：如果本地文件不存在但 `sync_state` 中有记录，标记为 `Deleted`
3. 如果本地出现新文件且 `sync_state` 中有同路径的 `Deleted` 记录，比较哈希：
   - 哈希不同 → 视为 `Modified`（覆盖远程旧版本）
   - 哈希相同 → 视为已同步，跳过
4. 删除远程旧版本，上传新版本（原子操作）

### 场景 2：单文件多次修改

**问题**：确保持续更新同一个远程文件。

**解决方案**：
1. `sync_state` 记录 `local_hash` 和 `remote_hash`
2. 每次同步时比较哈希：
   - 本地哈希变化 + 远程未变 → 上传覆盖
   - 本地未变 + 远程哈希变化 → 下载覆盖本地
   - 双方都变 → 冲突处理
3. 同步完成后更新 `sync_state` 中的哈希和时间戳

### 场景 3：选择性同步（排除大文件/非笔记文件）

**解决方案**：
1. 新增 `SyncConfig` 配置结构：
   ```rust
   pub struct SyncConfig {
       pub include_patterns: Vec<String>,    // ["*.md", "attachments/*"]
       pub exclude_patterns: Vec<String>,    // ["*.pdf", "*.zip"]
       pub max_file_size: u64,               // 最大文件大小（字节）
       pub exclude_dirs: Vec<String>,        // ["node_modules", ".git"]
   }
   ```
2. `ChangeDetector::scan_local` 应用过滤规则
3. UI 中提供配置界面

### 场景 4：跨设备同步（新设备拉取）

**解决方案**：
1. 新设备首次配置同步目标目录时，触发 `FullSync` 模式
2. `FullSync` = 下载远程所有文件到本地（跳过已存在且哈希相同的文件）
3. 初始化 `sync_state` 表记录
4. 后续进入正常增量同步模式

## 五、同步流程逻辑

### 5.1 增量同步流程

```
1. 读取 sync_state 表，获取上次同步状态
2. 扫描本地文件（应用 SyncConfig 过滤规则）
3. 获取远程文件列表
4. 对比三方数据（本地、远程、sync_state）：
   a. 本地有 + 远程有 + sync_state 有：
      - 三方哈希相同 → 跳过
      - 本地哈希变 + 远程未变 → 标记 Upload
      - 远程哈希变 + 本地未变 → 标记 Download
      - 双方都变 → 标记 Conflict
   b. 本地有 + 远程无 + sync_state 无 → 标记 Upload（新文件）
   c. 本地有 + 远程无 + sync_state 有 Deleted → 标记 Upload（重建文件）
   d. 本地无 + 远程有 + sync_state 无 → 标记 Download（跨设备新文件）
   e. 本地无 + 远程有 + sync_state 有 → 标记 Download（远程更新）
   f. 本地无 + 远程无 + sync_state 有 → 清理 sync_state 记录
5. 执行同步操作
6. 更新 sync_state 表
7. 返回 SyncResult
```

### 5.2 自动同步流程

```
1. 应用启动时读取自动同步配置
2. 启动后台定时器（默认 5 分钟，可配置 1-60 分钟）
3. 每次定时器触发：
   a. 检测网络状态（ping 同步目标目录 / 检查目录可访问性）
   b. 如果网络不可用，跳过本轮，记录日志
   c. 如果有上次未完成的同步（断点），从断点继续
   d. 执行增量同步
   e. 更新最后同步时间
4. 用户编辑笔记后，重置定时器（防抖 30 秒）
```

### 5.3 断点续传机制

```
1. 同步开始时，将当前操作写入 sync_state 表（status = 'syncing'）
2. 每完成一个文件的同步，更新 sync_state
3. 如果同步中断（崩溃、断电）：
   - 重启后扫描 sync_state 中 status = 'syncing' 的记录
   - 重新对比这些文件的本地和远程哈希
   - 从断点继续同步
```

## 六、异常处理机制

| 异常类型 | 检测方式 | 处理策略 |
|---------|---------|---------|
| 同步目标目录不存在 | `is_connected()` 检查 | 提示用户检查路径，暂停自动同步 |
| 文件读取权限不足 | `fs::read` 返回错误 | 跳过该文件，记录错误，继续其他文件 |
| 文件写入冲突 | 哈希对比检测 | 根据冲突策略处理（KeepNewer/KeepLocal/KeepRemote/KeepBoth） |
| 网络中断 | 目录不可访问检测 | 暂停同步，等待网络恢复后自动重试 |
| 同步中断（崩溃） | sync_state 中间状态 | 重启后断点续传 |
| 文件被占用 | 写入失败 | 重试 3 次（间隔 1 秒），失败后记录错误 |
| 磁盘空间不足 | 写入失败 | 停止同步，提示用户清理空间 |

## 七、数据安全保障

1. **哈希校验**：每个文件同步后计算 SHA-256，写入 sync_state，下次同步时校验
2. **冲突备份**：`KeepBoth` 策略下，本地文件备份为 `{name}.conflict-{timestamp}.{ext}`
3. **删除保护**：`sync_state` 记录已同步文件，只有确认本地删除后才删除远程文件
4. **原子操作**：上传完成后再更新 sync_state，避免中间状态
5. **敏感数据**：同步目标路径存储在数据库 config 表中（非 localStorage）

## 十、验证步骤

1. **构建验证**：`npm run tauri build` 成功
2. **手动同步**：创建笔记 → 扫描变更 → 同步 → 检查远程目录
3. **增量同步**：修改笔记 → 同步 → 只上传修改的文件
4. **冲突处理**：同时修改本地和远程同一文件 → 检测冲突 → 按策略解决
5. **选择性同步**：配置排除规则 → 同步 → 验证排除的文件未被同步
6. **跨设备同步**：新设备配置同步目标 → 全量拉取 → 验证所有笔记下载完成
7. **断点续传**：同步中途强制终止 → 重启应用 → 验证从断点继续
8. **自动同步**：启用自动同步 → 修改笔记 → 等待间隔 → 验证自动同步触发
